This is already happening

Agent security failures rarely come from the model alone. They happen at the tool boundary: a validator that misreads a command, a protocol message nobody inspects, a config file one agent can write for another.

  1. A sed validator bypass in Claude Code allowed arbitrary file writes

    CVE-2025-64755 (GHSA-7mv8-j34q-vp7q): GitHub advisory, OSV record

    Claude Code's command validation could be bypassed with sed features, turning a "safe" text edit into a write anywhere on disk. It was fixed in version 2.0.31 by blocking those sed commands.

  2. MCP sampling lets a malicious server drive the client's model

    Unit 42, Palo Alto Networks, 5 Dec 2025: New Prompt Injection Attack Vectors Through MCP Sampling. Related analysis: arXiv 2601.17549

    A server that issues sampling/createMessage can inject instructions into the client's model to steal resources, hijack the conversation or invoke tools covertly. The arXiv analysis notes that sampling requests carry no origin authentication.

  3. Coding agents can free each other by rewriting shared config

    Embrace The Red, 24 Sep 2025: Cross-Agent Privilege Escalation, with commentary by Simon Willison

    On a shared workspace, one agent writes another agent's .mcp.json, AGENTS.md or editor settings, which loosens its permissions.

  4. Argument injection turns pre-approved commands into code execution

    Trail of Bits, 22 Oct 2025: Prompt injection to RCE in AI agents

    Agents that allowlist "safe" utilities can still be steered into dangerous flags on those utilities. The write-up recommends -- argument confinement and narrow facades.

What the audit covers

Seven tool-boundary areas. Each maps to a validator in our open-source reference gateway, so every test has a working model behind it and a concrete fix design in front of it.

Registry pinningValidator R
Are tool schemas and descriptions pinned, and does a silent change (a rug pull) revoke trust? Includes Unicode lookalikes and hidden instructions in tool descriptions.
Workspace and shell confinementValidators W and S
What each allowed command actually does on disk: copies, moves, in-place edits, symlinks, redirects and permission changes. Protected config paths such as .git, .mcp.json, AGENTS.md, CLAUDE.md and .vscode. Arguments are canonicalized and confined behind --.
Taint and information-flow labelsValidators T, F and P
Once a session reads untrusted content, does the taint follow the data through files, workflows and approvals, and does it survive into the next session?
Exfiltration and encoding evasionValidators I and Z
Can a protected value leave in reversed, shifted, XORed, interleaved, hex, base32 or base64 form? We measure match coverage against the real matcher thresholds and report the transforms that get through.
Return-channel secret scanningValidator D
Secrets that arrive in tool results get pinned so they can't be sent back out. We test capacity limits, secrets split across fields, and whether the pinning runs on every transport.
Budgets across subagentsValidator V
When an agent forks subagents, do their combined actions stay within one budget? Vector-clock accounting across fork and join.
MCP protocol and transport desyncMCP wire proxy
JSON-RPC id matching, error responses, id reuse, batches, duplicate keys, parser differentials, and server-initiated sampling and elicitation requests. Anything that reaches the model without being inspected.

The kind of thing we find

These five findings come from a red-team audit of our own gateway on 31 October 2026, not from a client engagement. Each was reproduced against the code. The two critical findings include a short trace. The high findings state what is on main and what is still open. Working exploit code is not published.

CriticalCross-session taint lossAn untrusted file becomes trusted when a new session starts.

Trace

  1. Session A reads untrusted content and is correctly tainted.
  2. With a human-approved write, Session A creates data.json, labelled untrusted.
  3. Labels lived only in Session A's memory. Session B, on the same disk, sees data.json as trusted.
  4. Session B emails the file out, and the gateway allows it. Shell redirects were not recorded in the provenance ledger either.

Fix

File labels now persist across sessions in an append-only, hash-chained store. With a directory bound, a file with no record that is not older than the store epoch is untrusted.

Residual risk: network filesystems without stable inodes need a path-and-hash fallback.

Status: fixed on main (PR #34).

CriticalJSON-RPC id desyncA response with id "7" instead of 7 skips inspection.

Trace

  1. The proxy matches responses to requests by their serialized id.
  2. The client sends request 7. A malicious server replies with "7" or 7.0.
  3. The lookup misses, so the proxy forwards the response unchanged. The prompt injection inside is never scanned and the session is never tainted.
  4. Error responses, a reused id, list and subscribe methods, and server-initiated elicitation requests also pass without inspection.

Fix

Request ids stay null, string, or int, with no coercion between those forms. A response whose id is not in flight is not forwarded, malformed and reused ids are rejected, and every response that reaches the model is scanned, including errors.

Residual risk: a peer that stringifies an id has that response dropped rather than inspected. Pin one codec so ids are not rewritten between hops.

Status: fixed on main (PR #34).

HighIn-place edit launders file labelsAn allowed file edit can strip a file's sensitivity label.

The bug class

An allowed in-place edit that replaces a file's underlying inode can leave its sensitivity label behind, so a protected copy can later be sent out.

Fix design

The broker that ran the command publishes an old-to-new inode map, and labels move with it. Edited files are keyed by path first. The read-write <> redirect is rejected.

Residual risk: any utility that replaces an inode without the broker observing it.

Status: fixed on main (broker inode and rename maps on rebase).

HighSecret-store pin-stuffing and split secretsThe inbound secret store can be filled up or sidestepped.

The bug class

A tool result an attacker controls can exhaust the secret store's fixed capacity, and secrets split across fields can avoid being pinned at all.

Fix design

Separate evictable soft pins from non-evicting hard pins. Join adjacent fields before enrollment, and check outbound fields concatenated. When hard capacity is reached, raise a human-review lead and forward a redacted body.

Residual risk: secrets split non-adjacently with delimiters can still evade; these surface as review leads.

Status: pin-stuffing fixed on main (separate hard and soft stores). Split secrets: fix designed, not yet merged.

HighEncoding evasionReordered or encoded secrets can slip past the exfiltration matcher.

The bug class

Some byte reorderings and common text encodings keep a protected value below the exfiltration matcher's similarity threshold.

Fix design

Decode hex, base32, base64 and percent-encoding to a fixed point (at most four rounds), de-interleave strides 2 to 4, prefilter on byte histograms, then run the existing checks. Cost is O(n·k).

Residual risk, stated plainly: no finite matcher catches arbitrary encodings. What the fix doesn't catch becomes a human-review lead.

Status: stride, hex and base64 forms fixed on main. Other encodings remain out of scope.

Why AgentGate

We test against a working reference, not a checklist. AgentGate is an open-source (Apache 2.0) policy gateway that sits in an agent's tool loop. It is deterministic and built on the Python 3.12 standard library only. Its validators are opt-in and inert until attached, so each one can be read, tested and reasoned about on its own.

When the gateway sees untrusted input, it taints the session and attenuates the agent's capability so egress can't be turned back on. Held calls go to a human. We audit your stack with the same model, and our fix designs are written to the same bar.

We focus on three areas that get less attention than prompt injection itself:

  • JSON-RPC and MCP transport desync: the gap between what a proxy inspects and what a client or server actually accepts.
  • Vector-clock budgets across subagents: keeping forked agents inside one combined budget.
  • Canonical argument confinement: deciding on the arguments a tool will really receive, not on the string the model wrote.

The validator layer: R ∧ W ∧ F ∧ I ∧ P ∧ T ∧ S ∧ V ∧ D ∧ Z ∧ C ∧ E ∧ B ∧ A

Fourteen bounded, deterministic predicates in the Python 3.12 standard library. A call is admitted only if every attached predicate admits it; each one is inert until a trusted adapter attaches its state, and state is committed only after all of them pass. Denials use JSON-RPC codes -32066 through -32080. That is a statement about these seven papers, not the whole literature. T now persists labels across sessions; a replacement chain that hashes cleanly is not caught, which is the same class of residual as the provenance work above.

  • This is a reference design, not a deployed product. AgentGate is not a penetration test, a certification, a production WAF or an OS sandbox, and we make no detection-rate claims.
  • Evaluation cohorts are synthetic and written by the same author as the detectors. They show the code does what it says on those cases. They don't measure recall against an unknown adversary.
  • Benchmarks use test doubles. In the v14 reference package, the combined timing runs real code for some validators and stand-ins for the rest, so it is not a full-pipeline latency figure. In-memory cases measured below 2 ms at p99. The durable SQLite path measured 2.9 ms at p99, which exceeds that objective.
  • We can't promise a false-positive rate on natural text. A benign message can be an anagram of a protected one, so no distribution-free bound exists. A 10,000-message synthetic smoke test produced zero hits, which is a fixture result, not a corpus study.
  • Property-based tests find counterexamples. They are not proofs. The gateway suite has 23 Hypothesis state machines (counted in the test files on 31 October). The 31 October re-run used Hypothesis 6.140.0 rather than the pinned 6.170.9.

Questions

What's in scope?

The tool boundary of your agent system: which tools and MCP servers your agents can call, what they can read and write, what can come back into the model's context, and what can leave. It isn't a general pentest of your infrastructure or a review of model quality.

What do you never do?
  • We don't recommend automatic blocking. Detection leads go to human review.
  • The only automated action in our reference design is a 15-minute freeze of a registered internal agent credential. It lifts on its own and pages a human.
  • We never deploy honeypots on the public internet. Ours binds to localhost, and contact with a canary is treated as a lead, not proof of intent.
  • We don't push to your repositories. Fixes come as designs or pull requests that you review and merge.
  • We don't hand over exploit kits. Traces show the mechanism and how to fix it.
Is this a penetration test or a certification?

No. It's a focused engineering audit of the agent tool boundary. You get findings and fix designs, not a compliance attestation.
